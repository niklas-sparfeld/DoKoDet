# VisionDetector M4 — Real recognition handoff

## Decision

The local VisionDetector pipeline is ready for a real package, but recognition work is not ready
to start. The repository contains no real, human-labeled V1 evidence package. The existing raw
videos have event timing labels, not played-card identity labels. Do not train a card recognizer
from the current package fixtures or claim recognition quality from them.

Reviewed 2026-08-27 against the V1 evidence contract, the local M3 pipeline proof, and the current
dataset manifest.

## Evidence sizes and offsets

The shared upload fixtures contain manifests only. They do not contain JPEG files. Their declared
frame sizes and offsets are contract values, not measurements from an iOS capture:

| Source | Manifest size | Frames | Declared frame sizes | Present actual offsets | Missing offsets |
| --- | ---: | ---: | --- | --- | --- |
| `example-complete` | 3,774 B | 6 | 120,001–120,006 B; 720,021 B total | -802, -401, -101, +151, +399, +701 ms | none |
| `example-incomplete` | 2,249 B | 2 | 90,001–90,002 B; 180,003 B total | -799, +149 ms | -400, -100, +400, +700 ms |

The fixture upload command replaces the absent frame files with deterministic 42-byte placeholder
values, or 252 B for the six complete-package frames. The in-process M3 HTTP test uses a separate
23-byte placeholder value, or 138 B for the six complete-package frames. `file` identifies the
stored values as ASCII text, not JPEG images. This is transport-test data and must not be used as a
visual recognition sample.

The V1 capture contract uses six target offsets:

```text
[-800, -400, -100, +150, +400, +700] ms
```

The complete fixture has at most 2 ms of actual-offset drift. The incomplete fixture demonstrates
that the package can preserve present frames and report missing targets.

## Actual iOS package check

No app-exported or uploaded real iOS V1 package is present in this workspace. The local backend
package is generated by the fixture tests. The iOS source has a JPEG encoder and tests for complete
oriented-frame encoding, but that does not prove that a package from a physical capture reached the
backend.

Therefore, the answer to “do actual iOS packages contain decodable complete-frame JPEGs?” is
**not verified**. A real package must be collected and checked before recognition work begins.

available for recognition is therefore **zero**.

## Coverage gaps

- **Deck:** No card identity, physical-copy, or explicit deck label exists for the real recordings.
  The 40-card and 48-card contract manifests are defined, but neither is represented by a labeled
  V1 evidence package.
- **Lighting:** The recorded metadata reports room light. It does not cover daylight, low light,
  glare, hard shadows, or mixed light.
- **Camera:** The source set includes iPhone SE (2nd generation), iPhone 14, and iPhone X video.
  Most recordings use a fixed, high-oblique view with the table in context or filling the frame.
  No real V1 package confirms the final iOS camera orientation, dimensions, and JPEG output.
- **Play style:** 38 recordings are staged. The metadata records single-actor play, regular
  cadence, few mistakes, no game decisions, and mostly no overlapping plays. The five real-game
  recordings add real play but still lack card identity labels. The kitchen scenario adds long
  pauses and non-card hand/object motion, but it is not a played game.
- **Event-package labels:** There is no reviewed mapping from an event package to the played card,
  no physical-copy label, and no package-level quality or decode review.

## Evidence-contract limitation

The backend checks the declared media type, byte length, and SHA-256 hash. It does not decode JPEG
bytes. A sender can therefore label arbitrary bytes as `image/jpeg` and pass the current contract
if the manifest hash and size match. The M3 proof exposed this because its deterministic test bytes
are accepted and stored unchanged.

Before real recognition, add a real package decode check or a versioned contract rule that requires
decodable JPEG bytes. Keep the raw bytes and manifest hash unchanged when adding that check.

## Next gate

Collect at least one real game event with the iOS app. Export the complete V1 package, verify all
present frames decode as complete JPEGs, record the observed sizes and offsets, and label each event
with card identity, deck variant, and physical-copy information. Only then start the recognition
experiments in [plan 0022](../plans/0-to-specify/0022-Table_Evidence_Analyzer_Development.md).
